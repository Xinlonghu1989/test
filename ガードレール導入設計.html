入出力ガードレールの導入設計

2026-08-26 ｜ 対象：gradio_app_0825（PoC実装コードの確認に基づく）｜ STAGE 1（2026年10月〜）着手用

入力と出力の両方で、個人情報・有害情報を検出して制御するための設計です。 Amazon Bedrock Guardrails をどこに、どう入れるか。そして ガードレールだけでは塞がらない穴を、どこで塞ぐかを整理します。

結論

Bedrock Guardrailsは入れるべき。ただしそれだけでは足りない。

  1. 認可は守れない：「この人がこの資料を見てよいか」をガードレールは知りません。最大の情報漏えい経路は権限であり、そこは既存の権限台帳が唯一の防壁です。
  2. 日本語の検出に穴がある：氏名・住所・電話・マイナンバー・口座・社員番号は、正規表現と辞書の自前併用が要ります。
  3. LLMを通らない経路は対象外：履歴DB・ログ・Word出力に残る個人情報は、保存前のマスキングでしか防げません。

ただし、STAGE 1で新たに作るのは3つだけです（日本語PIIの検査／外部テキストの隔離／保存前マスキング。合計3〜4人日）。 最大のリスクである認可はすでに動いており、今回はそこへ検査層を重ねる作業になります。 → §4

設計上の制約が1つあります。 Guardrailsを「モデル呼び出しに同梱する」方式（guardrailConfig）は Converse／InvokeModel API の機能で、 現在のAnthropic互換エンドポイントでは指定できません。したがって ApplyGuardrail API を前後に別呼び出しで挟む構成を採ります。 この方式はモデル経路に依存せず、④⑤のような「モデルに渡す前のテキスト」にも使える利点があります。

2アーキテクチャ3層＋横断2つ

入力5系統を信頼度で分け、入口・モデル・出口の3層で検査する。認可と監査ログは全体を横断する。

実装の骨格

def chat(messages, *, feature, ...):
    # ① 入口：利用者入力・添付・外部テキストを、種別ごとに評価
    verdict = guardrails.check_input(messages)        # ApplyGuardrail ＋ 自前PII
    if verdict.blocked:
        applog.event("guardrail", feature, action="block", kind=verdict.kind)
        return _refusal(verdict)                     # fail-closed。素通ししない

    # ② モデル：マスク済みのメッセージだけを渡す
    answer = _call_model(verdict.masked_messages)

    # ③ 出口：応答を検査し、保存前にマスクした形へ
    out = guardrails.check_output(answer)
    response_store.save(out.masked)                   # 履歴DB・ログは常にマスク後
    return out.text

呼び出し側（27画面）は一切変更しません。ai_client が唯一の通り道であることが、 この設計が成立する前提です。

5費用と遅延の設計ここを外すと後で効く

Guardrailsはテキスト量に応じた課金です。RAGの根拠を毎回すべて検査すると、高額かつ低速になります。 検査の頻度を対象ごとに分けます。

対象頻度理由
①利用者入力／②添付テキスト毎回そのつど内容が変わる。混入を止める最前線
④ウェブ本文／⑤X投稿・見出し毎回外部・未検証。注入と有害表現の主経路
出力（モデルの応答）毎回最後の砦。保存前マスキングもここで行う
③RAG検索結果（社内資料）索引時に1回内容が変わらないので、毎回検査する意味がない。結果をメタデータに保存して使い回す

遅延は前後で2コール増えます（体感で数百ミリ秒）。現在の回答は30秒前後かかるため相対的な影響は小さいものの、 長文は分割して並列に評価します。
